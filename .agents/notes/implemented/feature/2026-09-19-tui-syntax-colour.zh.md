# Agent Note: Syntax colour for fenced code in the terminal

Status: implemented

[English](2026-09-19-tui-syntax-colour.md) | 中文

## Problem

编码 agent 是用代码作答的，而终端把这些代码全都画成同一种颜色。一个围栏代码块抵达对话记录时，只是夹在两道暗色围栏之间的纯文本行：关键字、字符串、注释与标识符是同一种灰，于是要找出真正要紧的那一行，就得逐词去读一整段回复。浏览器界面自交付之日起就以彩色显示同样的代码，靠的是 `packages/client/ui-primitives` 中的 shiki 高亮器；唯独终端没有。

pi-tui 并不缺什么。它的 `Markdown` 主题带有 `highlightCode(code, lang)` 这个钩子，缺省时便退回纯文本行——而终端一直传的正是缺省。

## Decision

`src/highlight.ts` 用一个为本界面构建的 shiki core 填上了那个钩子。

**跨界面只用一套高亮器。** 客户端已经以 shiki 加 JavaScript 正则引擎为标准——不带 oniguruma WASM——终端采用同一个 core，而不是另起一套带另一套配色的高亮器。终端是 Host 程序，因此它加载真正的配色主题模块，而不是客户端那套 CSS 变量主题。

**启动时什么也不加载。** 一份语法是几百 KB 的 TextMate 规则，而它的第一次分词会编译这些规则。语法表中每一项都是各自的动态 import，core 本身在第一个能解析出语言的围栏出现时才构建，而一个没有代码的会话这些统统不会加载。提出请求的那个代码块先画成纯文本，其语法则在渲染路径之外被导入并预热，随后应用被告知重新构建这一帧——`Markdown` 会缓存它渲染出的行，因此这次重绘会先让对话记录失效。

**配色主题由终端自身的背景选定。** 应用本来就要向终端询问背景色以构建淡入亮度阶梯；同一个回答也决定了取 `github-dark-default` 还是 `github-light-default`，于是浅色终端不会被塞进深色主题的配色。什么也不回答的终端取深色主题——那通常正是不作答的终端的样子。

**色深是单独判断的。** `resolveColorDepth` 只读 `COLORTERM` 与 `TERM` 来判断 24 位或 256 色，别的一概不看：要求 `reducedMotion` 的用户照样得到彩色代码，因为颜色不是动效。既不声明任何色深的终端、被禁用的调色板、`NO_COLOR`，以及 `codeHighlight: false`，都会把每个代码块画成纯文本。

**一个围栏绝不会毁掉一帧。** 分词是在渲染之中、对模型撰写的文本所做的第三方工作。导入失败的语法、加载器无法拆包的模块形状、以另一个名字注册的语法，以及抛出异常的分词器，都会让那门语言从此以纯文本绘制。只有当 `getLoadedLanguages()` 报出某个 id 之后，它才被信任。

## Alternatives considered

**把 shiki 的 scope 映射到调色板的九个角色上。** 已否决：调色板是语义化的——强调、成功、警告、错误——而语法不是。把关键字、类型、数字与标识符塞进三种颜色，付出的是大半的工作量、换回的只是一小部分效果；况且 css 变量主题自己的分桶就把标识符、类型与数字归进了同一个角色。配色主题之所以能区分它们，正是因为那本就是配色主题的用途。

**固定一张十六色 ANSI 配色表，而不用配色主题。** 作为默认形态已否决：终端原生的颜色确实会跟随用户自己的配色方案，但它们同样会压平一个主题的区分度，也表达不出注释与边框各自想要的那两种灰。色深判断已经拒绝了那些无法编码主题配色的终端，而那正是这条规则所针对的情形。

**像客户端对其启动语言那样，在启动时加载一小组语法。** 已否决：客户端的启动集服务的是一个已经打开的文档，而终端会话的开销是从敲下启动命令的那一刻算起的。大多数会话从不渲染任何围栏，而第一个渲染围栏的会话付出的是一次重绘，而不是让每个会话都去付一次启动代价。

**把工具卡片的正文——写入的文件、读取、差异——也一并高亮。** `read` 卡片的文件行与 `diff` 卡片的变更行现在经由本高亮器已经提供的同一条 `CodeSpan` / `paintCodeRows` 路径着色。[shell 模式草稿与 `$ command` 行的语法高亮](2026-09-22-tui-shell-syntax-colour.zh.md) 为 `!` / `!!` 草稿与 `$ command` 行着色。

**让代码块保持纯文本，直到反正会发生的下一次渲染。** 已否决：在用户注视之下落地的回复会一直是纯文本，直到某个无关的按键被按下。高亮器自己请求这一帧，这与流式淡入和子 agent 面板已经在用的那条先画出你有的、等它落地再纠正，是同一条。

## Consequences

- `@deepseek-ai/dsh-tui-app` 新增了 `shiki`、`@shikijs/langs` 与 `@shikijs/themes`。打包保持这些 import 为动态形式——`lib/index.js` 只增长了约 10 KB——因此语法随 tarball 一同发布，但只有在某个围栏需要时才从 `node_modules` 加载。
- 提供十七种语言。围栏若标注其他语言，则画成纯文本，不带信息的裸围栏也是如此。
- `codeHighlight` 以布尔字段加入受校验的配置，默认为 true。
- 某门语言的第一个围栏代码块会被画两次：一次纯文本，一次彩色。若对话记录已越过渲染器的重绘窗口，第二次绘制便无法进行，那个代码块也就保留它当时的颜色。
