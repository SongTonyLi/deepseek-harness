# Agent Note: Reuse each transcript block's last drawing in the terminal

Status: implemented

[English](2026-09-19-tui-transcript-render-reuse.md) | 中文

## Problem

pi-tui 的主屏渲染器每一帧都向每个已挂载组件索取其行，并把整帧与上一帧逐行比对。终端对话记录从不裁剪，所以一帧要做的工作随会话增长。`packages/bundle/tui-app/src/blocks.ts` 中有三种块每帧都从头重建自己的行，而工具卡片则不论折叠与否，每次都对每张 `read`、`edit`、`write` 卡片的代码行运行 shiki 分词器。回复流式输出时帧请求最高达 60 Hz，agent 运行期间旋转指示器以 12.5 Hz 请求，任何渐变在动时则为 30 Hz，于是一帧一旦超出其周期，进程就在这一回合剩余时间里被钉在满 CPU 上，每次按键都要排在它后面等待。在包内 bench 上测得——每回合一张折叠的 TypeScript `read` 卡片加一段带代码围栏的回复，之上是 1500 行系统提示词：80 回合时一帧空闲帧耗时 455 ms，若 `src/app.ts` 中的渐变与焦点守卫再把对话渲染一遍，则为 910 ms；带守卫的帧在 20 回合约 240 ms，在 320 回合为 3.9 s；关闭代码着色后 80 回合的空闲帧为 31 ms，因此分词器约占成本的 93%。

## Decision

每个块保留上次画出的行以及构建它们所用的键——宽度、焦点标记条是否收窄了它、折叠状态，卡片还包括其状态与结果——并在键不变期间原样交回。`invalidate()` 会丢弃它们，而应用在语法落地时本来就会对每个块调用它；新的终端宽度则自然会让每个键都不再匹配。每帧都会变化的内容画在保留的行之上而不是写进其中：卡片渐变重新着色保留的分组，焦点标记在前面加上标记条，而正在流式输出的回复因其尾部按词龄重新着色，仍如以前那样每帧重新组合。回复还把上次 Markdown 解析所着色的围栏保留在一个以语言和源码为键的备忘中，因为 pi-tui 的 `Markdown` 在每次文本变化时都重新解析整条消息并再次要求主题为每个围栏着色；备忘直接回答它见过的围栏，并在下一次解析结束时丢弃那次解析没有索取的一切，因此它保留的从不多于回复所显示的。高亮器留作纯文本的围栏不被保留，于是落地的语法会被再次问到它。

每块一条记录、每条回复一次解析所含的围栏，把内存限定在对话记录本来就保留的范围之内，因此不引入任何缓存大小、淘汰策略或配置。聚焦一张卡片会重建这一张卡片，因为标记条收窄了它并改了它的折叠键；每次按键重建一张卡片是可以接受的。

## Alternatives considered

**一个按源码与语言为键、以 LRU 限界的进程级高亮器缓存。** 否决：该上限是一个没有部署含义的可调参数，而与所服务的块共存的备忘会在会话切换时随块一起释放，无需任何策略。

**把着色后的行与换行后的行分开缓存，使焦点变化或宽度变化只重新换行而不重新着色。** 暂时否决：尺寸变化无论如何都会改变每个块的宽度键，而焦点变化只重建一张卡片，所以第二层缓存每次按键只能省下一次分词。

**从对话记录容器中裁掉旧块。** 否决：终端的回滚缓冲区拥有历史，键盘遍历与阅读器要寻址每一个块，而 pi-tui 只重绘变化的行，因此一个只花一次键比较的已稳定块，比决定丢弃什么更便宜。

**让沉降守卫复用交给它的那一帧，而不是再把对话渲染一遍。** 块一旦复用其行便不再需要：守卫的第二次遍历现在返回的是保留的数组，测得的聚焦帧与空闲帧相等。

## Consequences

- 改动后同一 bench：空闲帧在 20 回合为 1.2 ms，80 回合为 4.4 ms，320 回合为 18 ms；带渐变或焦点守卫的帧分别为 1.6 ms、4.5 ms 与 21 ms；80 回合下展开全部卡片为 0.7 ms，之前为 3.4 s。剩下的是 pi-tui 自己对整帧每一行的遍历，它随帧的文本增长，且在本包之外。
- `tests/blocks.spec.ts` 用一个计数高亮器钉住这份契约：一张卡片在重复的帧之间只着色一次，折叠或展开时再着色一次，`invalidate()` 之后再一次；一条回复在流式增量与提交之间对未变的围栏只着色一次；留作纯文本的答案会被再次问到；已稳定的块在没有任何变化之前返回同一组行。
- 测量来自包内 bench 之上的假终端，不包括终端模拟器与模型延迟。正在流式输出的回复只对最后一个已关闭围栏之后仍打开的尾部重新词法分析，消息末尾尚未闭合的围栏在闭合之前每次增量都会再着色一次。
